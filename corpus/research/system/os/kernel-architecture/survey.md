# Kernel Architecture: Problems, Mechanisms and Obligations

## Thesis

Kernel architecture changes **who may choose policy, modify state, execute work, coordinate a result and retain state across replacement**. Microkernel, exokernel, library OS and safe-language OS identify useful implementation families; they do not establish which dependency a design removes or which guarantee remains. The better comparison is: required behavior → obstructing dependency → architectural transformation → retained obligation → displaced cost.

This narrative survey uses 44 sources: five reviews/retrospectives, fifteen core design/evaluation readings and twenty-four targeted related readings. Four reviews were read through their bodies; one selectively. Evidence concerns publication-era prototypes; no experiments/proofs were reproduced and coverage is not exhaustive. The ledger records actual depths.

The reviews frame invocation granularity [EXT96](<../../../../../.obsidian/zotero/pdfs/NRYT8SSU.pdf>), customization/integrity [DENYS02](#^denys02), dependable decomposition [REL06](#^rel06), L4 experience [L4RET13](<../../../../../.obsidian/zotero/pdfs/8PYHHYL5.pdf>), and adoption [UMLR23](#^umlr23). Their taxonomies guide comparison rather than certify security or performance.

## Development timeline

**Kernel architecture develops along parallel problem paths.** The milestones below sample this survey's 44-source corpus, spanning 1968–2025. Dates identify publications, not the birth of systems or ideas. Arrows order selected work within a path; they do not establish direct influence or replacement. Gaps reflect coverage.

Selected foundations: [THE (1968)](#^the68) structures dependencies through a hierarchy; [HYDRA (1974)](#^hydra74) organizes objects and protected authority. Both make relationships explicit before the later debates over kernel forms.

**The paths intersect:** language contracts support both composition and replacement; specialization can enable policy customization but complicate compatibility; locality changes sharing and recovery costs. This is why the same architectural form can address different problems across decades.

**Boundaries need not coincide.** Policy ownership, protection, execution/accounting, sharing and lifetime are distinct relationships; separating them must preserve necessary dependencies. Nooks' extensions remain ring 0 and DMA is outside its protection; RedLeaf's immutable borrowing/object transfer/failure cleanup does not settle irreversible I/O. seL4 refinement and ASTERINAS' memory-safety foundation establish different properties [SEL409](<../../../../../.obsidian/zotero/pdfs/D95IYDV9.pdf>), [ASTERINAS25](<../../../../../.obsidian/zotero/pdfs/JY8VWH98.pdf>).

**A faster path may preserve the contract or narrow it.** LegoOS restricts shared-memory/process cases; Helios excludes a process spanning kernels [LEGO18](<../../../../../.obsidian/zotero/pdfs/EHTCF2AA.pdf>), [HELIOS09](<../../../../../.obsidian/zotero/pdfs/2FFMVSEM.pdf>). The scalable commutativity argument has specification/proof assumptions [SCR13](<../../../../../.obsidian/zotero/pdfs/TD9UXVAP.pdf>), [SCRPROOF18](#^scrproof18); it is not an automatic implementation generator. Explicit construction also changes the inherited-state obligations discussed by the position paper [FORK19](#^fork19).

THE's hierarchy and HYDRA's multiple object/protection relationships already caution against one universal partition [THE68](#^the68), [HYDRA74](#^hydra74). ExtMem likewise changes where policy/fault work executes without eliminating every memory-management dependency [EXTMEM24](<../../../../../.obsidian/zotero/pdfs/4J5WSFEI.pdf>).

## Decisive evidence

- **Linux scalability:** local kernel/application repairs improve a coherent 48-core system; tmpfs and selected workloads bound the result. A new overall architecture is not automatically necessary [LINUX10](<../../../../../.obsidian/zotero/pdfs/PGYH6U5Z.pdf>).
- **Sharing:** Corey's private mappings help independent faults, while shared subtrees avoid repeated mapping work. The needed sharing contract determines the useful partition [COREY08](<../../../../../.obsidian/zotero/pdfs/WNLMAW8G.pdf>). Barrelfish's evaluated messaging transport itself uses coherent shared memory [BF09](<../../../../../.obsidian/zotero/pdfs/4NEB78HN.pdf>).
- **Composition:** FlexSC can lose on isolated calls while winning with overlap/batching. Protected interaction cost depends on scheduling and working sets [FLEX10](<../../../../../.obsidian/zotero/pdfs/KGFM3XKG.pdf>).
- **Correctness:** seL4's reported 224-cycle optimized IPC path was outside its then-verified code. Proof and best performance must refer to matching configurations [SEL409](<../../../../../.obsidian/zotero/pdfs/D95IYDV9.pdf>).
- **Recovery:** Nooks prevents 313 of 317 trials that crash native Linux, yet VFAT corruption occurs in 90% of recovery cases; synchronization reduces that to 10%. Kernel survival does not establish persistent correctness [NOOKS03](<../../../../../.obsidian/zotero/pdfs/NYBLUDCD.pdf>).

Compare useful operations under matched behavior, threats, resources, timing endpoints and code changes. IPC cycles, service throughput, API support, memory safety and successful restart establish different claims.

## Research and reading

Three questions follow from the comparisons; they are proposed investigations, not established novel gaps:

1. **Can delegated policies compose under shared pressure?** Measure attribution, validation, starvation and shared bookkeeping when independently valid schedulers/pagers compete.
2. **When is separation cheaper than local repair under the same contract?** Match authority and observable semantics; vary sharing, aliases, payload, concurrency and topology. Charge reserved cores, metadata and reconciliation, and add legacy sharing requirements incrementally.
3. **Can evolution preserve client progress and irreversible effects together?** Inject faults around submission/completion; distinguish lost, duplicated and corrupt effects, surviving clients, state conversion and failed replacement.

### Reading plan

Follow one cut from reviews through core mechanisms and targeted counterexamples; compare the same operation and retained contract. Deepen uncertain comparisons. Publication requires reproducible searches, screening and gap validation.
